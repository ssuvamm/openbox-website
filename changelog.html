v1.6.101 FIX 2026-05-12
ROOT CAUSE FIX for the 3-report Portainer 422 class-level bug: Portainer 2.41 changed `--admin-password-file` to expect plaintext (not bcrypt)
  • 🔴 Sparkboxfan #8799, GamerX06 #9622, LaggyGamerZA #9024 — three completely independent installs, three identical 422s on Portainer admin login, one shared root cause finally pinned down today. LaggyGamerZA's diagnostic was conclusive: `bcrypt.checkpw(plaintext, hash)` returned True locally, Portainer's docker log confirmed 'created admin user with the given password', yet POST /api/auth still rejected with 422.
  • 🔴 Root cause: Portainer 2.41 silently changed `--admin-password-file` semantics from 'contains bcrypt hash' to 'contains plaintext' (Portainer now applies its own bcrypt before storing in /data/portainer.db). OpenBox has been giving it a pre-bcrypted hash since v1.0 — under 2.41 that string got stored AS-IF it were the plaintext password. Portainer then bcrypt'd our bcrypt-string, stored bcrypt(bcrypt_hash), and the user's actual generated plaintext never matched on auth. v1.6.99 (repair-portainer CLI) and v1.6.100 (silent-crash hotfix) shipped a user-rescue but used the same bcrypt-in-file approach, so didn't fix the root cause.
  • 🟣 Fix: three call sites, same semantic change — write PLAINTEXT (not bcrypt) to the secret file. install.sh's Portainer password block dropped the htpasswd/python3-bcrypt/docker-httpd:alpine fallback chain entirely. openbox CLI's cmd_repair_portainer and cmd_up self-heal both updated the same way. Confirmed in the wild before shipping: LaggyGamerZA ran the manual plaintext-replacement test and reported 'login now works with the provided username and password.'
  • 🟣 cmd_up detection logic flipped — old check 'heal if file does NOT have $2 bcrypt prefix' is now 'heal if file DOES have $2 prefix' (it's a legacy v1.6.100-or-earlier file that needs regenerating). Upgrading users auto-heal on next `openbox up` without needing repair-portainer.
  • Manual recovery for v1.6.100-or-earlier on Portainer 2.41: `sudo openbox update && sudo openbox repair-portainer`. The auto-heal on `openbox up` also catches it, but repair-portainer is faster (single command, with verify-login step before exit).
v1.6.100 FIX 2026-05-12
Hotfix: `openbox repair-portainer` verify loop crashed silently — `((_attempts++))` returned exit 1 under `set -e`
  • 🔴 LaggyGamerZA #9024 (90 minutes after v1.6.99 shipped): pasted full terminal output ending at 'Verifying admin login against http://127.0.0.1:9000/api/auth...' with no subsequent line — shell just returned to prompt. v1.6.99's cmd_repair_portainer used `((_attempts++))` to increment the retry counter; post-increment evaluates to the OLD value (0 on first iteration), which is exit code 1 in bash arithmetic context, which under the script's `set -euo pipefail` silently killed the whole script.
  • Critical UX note: the actual repair (docker rm ob-portainer, wipe modules/core/config/portainer, regenerate bcrypt hash, write state/portainer-admin-password.txt, docker compose up -d portainer) ALL already succeeded by the time the script crashed. Only the verify-and-report stage got skipped. Users who ran v1.6.99's command saw 'Verifying...' then prompt return, likely thought it failed — their Portainer was actually healed, new creds in state file.
  • Fix: replaced `((_attempts++))` with `_attempts=$((_attempts + 1))`. Assignments always return exit 0, so the loop now iterates all 10 retries as intended. Reproduced in isolation: `bash -c 'set -euo pipefail; _x=0; ((_x++)); echo after'` exits silently with code 1. Added inline comment at the fix site so the trap doesn't get reintroduced.
  • Manual recovery for anyone on v1.6.99 who hit this: your Portainer is almost certainly fine. Run `sudo cat /opt/openbox/state/portainer-admin-password.txt` to read the new credentials and log in. Or upgrade to v1.6.100 and re-run `sudo openbox repair-portainer` to see the proper 'verified (HTTP 200)' confirmation.

v1.6.89 FIX 2026-05-11
Egress check no longer false-fails on `webhook.crushcodeworks.com`'s 404 response (drop `curl -f`)
  • Issue: Both install.sh's egress probe and `openbox doctor`'s egress probe ran `curl -fsS -o /dev/null -m 10 https://webhook.crushcodeworks.com`. The `-f` flag tells curl to exit non-zero on any HTTP response ≥ 400. `webhook.crushcodeworks.com` is a Cloudflare Worker that only serves POST endpoints (license activation, support auth-key, crash telemetry); a bare GET to its root returns 404 by design. So every working install on every supported network was reading "reachable but 404" as "unreachable," which is the opposite of the truth. The user-facing "containers can't reach webhook" copy then implied a network problem that didn't exist.
  • Dropped `-f` from both curl invocations (`install.sh` line 1389, `openbox` line 3429). The check is now `curl -sS -o /dev/null -m 10 https://webhook.crushcodeworks.com` — exits 0 on any HTTP response (including 4xx), which is exactly what we want for a reachability probe. A real network outage still fails the check (curl exits non-zero with no HTTP response), and a TLS-MITM captive portal still fails (cert validation breaks before any HTTP response is exchanged) — so the check still catches the original `DEFAULT_FORWARD_POLICY=DROP` bug it was written for in v1.5.x. Added an inline comment at both sites explaining the `-f` history so a future maintainer doesn't "clean it up" by re-adding the flag.

v1.6.82 FIX 2026-05-10
`openbox up` now hard-fails with a clear "use sudo" hint when invoked without write permission to the install dir
  • Issue: `cmd_up`'s Portainer self-heal block writes to `${OB_ROOT}/modules/core/config/portainer-admin-password` and `${OB_ROOT}/state/portainer-admin-password.txt`. Both writes are wrapped in defensive `2>/dev/null || true` redirections to survive other failure modes (htpasswd missing, openssl too old, etc.). When a non-root user invokes `openbox up`, those redirections also eat the `Permission denied` errors — so the regen log line "Portainer secret missing or invalid — regenerating..." prints, the writes silently fail, no `[OK]` line follows, and the user is left with a Portainer that drops into its first-run wizard with no admin file. Worse, the user has no signal that the root cause was missing sudo — they assume our self-heal is broken and chase the wrong layer.
  • Added a perm-probe at the top of `cmd_up` (right after `cli_acquire_lock` + the trap, before `banner`). Probe is `mkdir -p ${OB_STATE_DIR}` + `touch ${OB_STATE_DIR}/.perm-check` + `rm` of the probe file, all in a subshell with stderr suppressed. If the probe fails, log a clear `Cannot write to ${OB_STATE_DIR} — openbox up needs to run as root` followed by the exact `sudo $0 up $*` re-run command, then exit 1 (the trap releases the lock cleanly). Dashboard-spawned `openbox up` is unaffected — the dashboard container runs as root inside the container so the probe always passes for that path. Only `cmd_up` is gated in this patch; if the same half-fail mode shows up in `cmd_restart` / `cmd_update` / `cmd_enable` / `cmd_disable` we'll add the same probe to those (likely worth doing proactively next round, but keeping this patch narrow).
